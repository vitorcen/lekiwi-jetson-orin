机器人动作录制与 MCP 动态调用

机械臂 + 三轮底盘共 9 电机 · 一动作一文件 · 新动作自动发现 · 人工控制永远优先 · 2026-07-31

已按独立评审的 P0/P1/P2 修正实施：播放器移入 base_host，MCP/GUI 降级为本机 control socket 薄客户端， motion_action 定级 4（最低），补齐崩溃矩阵，并删掉 catalog_revision / undo_token / sample_hz / CAS / 锁目录 / 逐帧 TTL。板上真机联调尚未进行。

结论先说

  • 在 GUI「主臂遥操作」面板增加动作名、录制范围、开始/停止、预览、保存，以及板端动作列表和删除。MVP 录机械臂，数据结构和板端录制器从第一天就支持后续同步录制机械臂与三轮底盘。
  • 录制器放在 base_host 执行层，不放 Mac GUI：它以同一个单调时钟采集经过仲裁和限幅的机械臂 dq[6] 与底盘 vx/vy/omega，所以键盘、Jetson 手柄和主臂都能进入同一动作。
  • 播放器也在 base_host，不在 MCP 进程（评审 P0 修正）。MCP 与 GUI 都只是本机 Unix control socket 的薄客户端；绝不用 MCP 经 ZMQ 流动作帧。这样双域 lease 是进程内一次判断，锁文件、逐帧 TTL、双域 ack 计数、CAS 删除整套分布式补丁全部消失。
  • 板端用一动作一 JSON 文件作为唯一真相源；没有额外 manifest。GUI 经现有 SSH 信任链调用板端管理 CLI，板端校验后临时文件 + fsync + 原子改名。
  • MCP 永久只暴露四个稳定工具：motion_action_list、motion_action_play、motion_action_stop、motion_action_status。现在就使用通用命名，避免加入轮子后破坏接口。
  • 不要为 yes/no 动态创建两个 tool。工具表缓存、重名、删除同步都会制造垃圾状态；动作是数据，不是 API。
  • GUI 的删除是可恢复的管理操作：正式文件原子移动到 .trash/，不向 LLM 暴露删除工具；播放中的动作拒绝删除。
  • 全身动作必须原子取得底盘和机械臂两个 lease：校准/总安全门 > pad > gui > ros > mcp > motion_action（motion_action 优先级 4，最低）。任一域出现人工或 ROS输入，整个动作立即抢断、底盘归零，绝不偷偷续播；结果里 by 指名是谁抢的。

1 · 现有链路与最小改动点

现有事实直接复用不能继续凑合的地方
Mac GUI 的 Rust leader worker 读取 1–6 号主臂舵机，约 30Hz 计算 dq = joint - zero 把 dq[6] 送到板端，由统一录制器采集实际采用后的目标 不能保存主臂绝对 raw position；一旦重新校准就失效
base_host.Arm.follow() 执行 ARM_MID + dq，并按六关节校准范围和每帧步长限幅 录制和播放都走同一条 follower 解释逻辑 不能在 MCP 里复制限位算法，安全约束必须留在串口唯一所有者
GUI 已通过 SSH 调板端状态，主臂命令走 ZMQ GUI 通过 SSH 调板端 motion_actionctl；CLI 再连本机 Unix control socket ZMQ PUSH 没有应答，既不适合传文件，更不适合当播放通道——所以动作帧永远不走 ZMQ
Hermes 已挂载 vlm 和 drive 两个 stdio MCP server 增加一次 motion_actions server 配置，之后动作变化不改配置 机械臂原本没有像底盘那样的 owner mux；现在补一条「最后一帧人工 arm 输入起 0.5s 内人工持有」的时间 lease，够用且不改现有行为
核心数据选择 机械臂保存相对“校准中位”的 dq[6]；底盘保存机体坐标系 vx/vy/omega，不保存三个轮子的 raw speed。播放时仍由当前机械臂校准和当前三轮运动学做最终解算与限幅，因此校准、轮径或底盘参数变化不会让动作文件直接绑定旧硬件数值。

2 · 推荐架构

GUI 和 MCP 都只发管理/播放命令，不持有动作数据，也不流运动帧；base_host 同时是唯一 canonical recorder、唯一播放器和九电机唯一执行者。这样以后接入 Jetson 手柄、Mac 键盘或其他人工源，不需要把输入事件跨机器拼接。

为什么播放器必须在 base_host 里（评审 P0，已采纳） 早先的方案把调度器放在 MCP 进程、用 src=motion_action 的 ZMQ PUSH 帧流给 base_host，仲裁留在 base_host。那样「原子取得双 lease」是空头支票：中间是一条无应答通道，MCP 只能先 status 再开播，典型的 check-then-act。更糟的是串口掉线时 base_host 会 exit(1) 让 systemd 重启（这是设计好的行为），重启期间 MCP 还在流帧，新起的 base_host 刚把臂唤醒到当前位姿就会执行半截动作的旧帧——逐帧 TTL 挡不住，因为帧是新鲜的，死掉的是上下文。 把播放器搬进 base_host 主循环后，lease 判断变成进程内一个 if，而 ZMQ 流帧、逐帧 ttl_s、双域 ack 计数、.locks/ 锁目录全部消失，MCP 崩溃语义（socket 断＝中止）自动正确。

草稿只活在 base_host 内存里，重启即蒸发（评审 P0，已采纳） 串口抖一下（USB 重枚举，这机器上真实发生过）→ exit(1) → systemd 重启 → 录了十几秒的动作无声消失。所以 status 返回 host_started_at；GUI 每次刷新对比这个 epoch，一旦变了而本地还握着草稿，就写一行「base_host 已重启，板端内存里的录制草稿已丢失」，而不是停在 board_draft 等一个不存在的 draft。
动作 ID 规则 MVP 使用 [a-z][a-z0-9_-]{0,31}，因此 yes、no 直接合法。显示名和描述以后可单独增加；不要把用户输入静默改写成另一个 ID。

字段规则理由
schema_version初始固定为 1；未知版本拒绝禁止猜测兼容导致九电机执行错数据
action_id等于文件名；全目录唯一消灭文件名和 manifest 两份映射
label / description给人和 LLM 的语义，不参与执行。label ≤60 字、description ≤200 字；只拒绝控制字符（<0x20 和 0x7F），不做字符白名单LLM 可据此选择 yes/no，而不是猜 ID。description 原文会进 LLM 上下文，所以要限长；但机器人说明本来就是任意语言的人话，白名单是荒唐的（评审 P2，已采纳）——真正有害的是把换行和终端转义序列偷进日志与提示的控制字符
tracks允许 arm、base 或两者同时存在；至少一条同一个 schema 覆盖机械臂、底盘和全身动作，不造三种文件
t_ms从 0 开始，严格递增，来自单调时钟系统时间跳变不能改变动作节奏
arm.frames[].dq正好 6 个有限整数；相对校准中位，导入和播放都限幅重新校准后仍可安全解释旧动作
base.frames[]vx_mps/vy_mps/omega_dps 为有限数，保存前已过 base_host 最终钳位动作表达车体运动，不绑定 7/8/9 三个电机 raw speed
总体上限15s、每轨 600 帧、每轨至少 3 帧、总时长至少 200ms、文件 ≤256KiB全身短动作足够；限制 LLM 阻塞时间和恶意文件

机械臂动作只有 tracks.arm，底盘动作只有 tracks.base，全身动作同时有两者。列表中的“范围”由轨迹键推导，不额外保存 scope 第二真相。几百帧只有几十 KB，没有必要在 MVP 做压缩或曲线拟合。

schema 里没有 sample_hz（评审 P2，已采纳） t_ms 已经是关于节奏的唯一真相。base_host 主循环 50ms poll、每帧 dq 还有串口事务开销，所谓「30Hz」只是名义值；把它写进 schema 等于给自己造第二份真相，两份必打架。采样只有一条下限规则（相邻样本至少 30ms，否则不携带新信息），写在 player.MIN_SAMPLE_PERIOD_S，不进文件。
为什么绝不录三轮 raw speed 7/8/9 号电机速度是底盘运动学的派生值。把派生值存盘会绑定当前轮径、安装角和符号；保存 vx/vy/omega 才能让同一动作经过未来修正后的运动学继续正确播放。

板端统一录制器

输入源录制点写入轨迹
Mac 键盘 ZeroMQbase mux 接受并完成最终速度钳位后tracks.base
Jetson 遥控器底盘摇杆同一个 base mux，不依赖 GUI 收到手柄事件tracks.base
Mac 主臂跟随Arm.follow() 完成中位映射、范围与步长限幅后tracks.arm
Jetson 遥控器机械臂按键/摇杆Arm.step() 完成积分和限幅后，换算为 raw-ARM_MIDtracks.arm

录制是被动观察者，不取得运动 owner，也不改变现有优先级。sampler 每个主循环 tick 读取两个域当前“实际采用的 canonical target”，以同一个 t0 生成时间戳；输入源中途切换也不会破坏同步。watchdog 停车后 canonical base target 立刻写成 (0,0,0)（评审 P1，已采纳）——键盘停发 0.5s 轮子已经停了，此刻若还采到最后一次速度，回放就会凭空多开一段车。总安全门关闭时同理归零。

控制通道 base_host 增加仅本机可访问的 Unix control socket /run/lekiwi/base_host.sock，处理 record / play / stop / status / save / delete / restore。落地方式是 systemd 的 RuntimeDirectory=lekiwi + RuntimeDirectoryMode=0750（评审 P1，已采纳：/run/lekiwi 不会凭空存在，User=jetson 也创建不了 /run 下的目录），socket 本身 chmod 0600——文件权限就是鉴权。SSH 只负责在板端启动 motion_actionctl，CLI 再访问本机 socket。不要给局域网新开无鉴权录制端口，也不要把管理命令塞进 fire-and-forget 的 ZMQ PUSH。
创建失败时 base_host 照常启动遥控并打一行 WARNING：让底盘因为一个 runtime 目录而瘫痪是更坏的交易；动作功能则在客户端明确报 host_unreachable，不半死不活。

原子保存

GUI -> ssh jetson motion_actionctl record-start --scope arm|base|full
  -> base_host canonical recorder creates an in-memory draft (lost on restart)
  -> GUI -> motion_actionctl record-stop        (store.validate_tracks decides valid/invalid)
  -> GUI preview / discard / motion_actionctl save <action_id> [--overwrite]
  -> store.validate_action  (the ONE validator: base_host, CLI and MCP share it)
  -> write yes.json.tmp.<pid>
  -> flush + fsync
  -> rename to yes.json
  -> fsync directory
  -> return {ok, action_id, scope, duration_ms, frames, replaced}

可恢复删除

GUI: the action id typed in the box must match the row     (visible confirmation)
  -> ssh jetson motion_actionctl delete yes
  -> base_host: refuse with action_in_use if THIS action is playing
  -> rename yes.json to .trash/yes.20260731T103500.json
  -> fsync active directory and trash directory
  -> return {ok, action_id, trash_name}
  -> undo = motion_actionctl restore yes.20260731T103500.json
  • 删除是原子改名，动作会立刻从 GUI 和下一次 MCP list 消失；当前目录永远没有半删除状态。
  • .trash/ 列表按删除时间倒序（不是按文件名，否则 zebra 会排在刚删的 apple 前面，撤销就会还原错动作）。撤销就是 restore <trash_name>，不做 undo_token（评审 P2，已采纳：token 只是给 restore 加了一层间接）。若 ID 已被新动作占用，restore 返回 action_exists 而不是覆盖。
  • 回收目录默认保留 30 天，清理只由显式的 purge-trash 完成——没有任何自动清理会在背后吃掉用户录的东西。
删掉的并发机制：expected-sha256 CAS 与 .locks/（评审 P0/P2，已采纳） 「两个 GUI 并发覆盖同一个动作」是假想敌：单操作者、十几个动作。真正需要的互斥只有一条——不能动正在播放的东西——而播放器现在就在 base_host 里，于是它退化成单进程里一个 play_action_id 变量比较。_refuse_if_in_use() 同时被覆盖保存和删除调用，所以两者语义统一（评审 P2，已采纳：原方案播放中删除被拒、播放中覆盖却隐式放行）。锁文件目录、共享/独占锁、digest 比对整段删除。
动作目录 ~/.local/share/lekiwi/motion-actions/*.json 是活动动作，.trash/*.json 是可恢复删除项；都属于运行数据，不提交 Git。仓库只提交 schema、导入器、MCP server、单测和示例动作。

5 · MCP 契约：稳定工具，动态数据

READ motion_action_list

无参数。每次调用直接读并校验动作目录（不经 control socket，所以 base_host 挂了也看得见目录），返回 ID、范围、标签、描述、时长、每轨帧数。坏文件单独列在 invalid，不让整个目录失效。

RUN motion_action_play

参数只有 action_id。不开放速度倍率、关节覆盖或 repeat；一条阻塞的 control-socket 请求，base_host 按录制节奏播放并在完成或抢断时回复。MCP 进程死 → socket 断 → base_host 立即中止，这就是全部的崩溃语义，不需要逐帧 TTL。

STOP motion_action_stop

幂等。抢断当前动作（不论是 MCP 还是 GUI 预览发起的），底盘立即发零速；机械臂保持当前安全目标，随后走既有 idle relax 策略。没有动作在播时返回 result: idle。

READ motion_action_status

返回 active action、范围、进度、base/arm owner、总安全门、arm state、录制/草稿状态、host_started_at、最后结果。LLM 不得把“调用返回了”称为“执行成功”——result 不是 succeeded 就是没做完。

timeout 必须盖过 15s 动作上限加机械臂靠近首帧的时间，因为 motion_action_play 是阻塞的。板端源码随 board/ 一起 rsync 到 /home/jetson/motion_actions/，与 base_host.py 同级——两者 import 同一个 store，schema 校验只有一份。

“自动暴露”到底是什么意思 保存后，下一次 motion_action_list() 立刻能看到新动作及其 scope；删除后，下一次 list 立刻不再返回它。整个过程不改 YAML、不 reload MCP、不重启语音 daemon。机器人提示词只需规定：“涉及姿态或移动动作时先 list，再按 ID play。”
LLM 没有删除权限 delete/restore/purge 只存在于板端管理 CLI，并只能由 GUI 经 SSH 调用。MCP 不增加 motion_action_delete；提示注入或模型误判不能删除用户录制的数据。

6 · 播放与安全语义

层规则失败行为
动作文件纯 JSON、严格 schema、每轨长度/帧数/数值上限拒绝加载；绝不执行任意脚本或表达式
MCP / CLI 客户端只发一条阻塞请求，不持有调度器、不流帧、不碰串口host_unreachable / busy / unknown_action / recording 等明确返回；连接断开＝中止
双域 lease（base_host 进程内）base 与 arm 分域；全身动作必须在同一个 tick 里一次性拿到所需全部 lease，否则一个电机都不动任何一侧出现人工或 ROS 输入，整个动作 preempted 并带 by，底盘立停，另一轨也不续播
底盘优先级 muxpad 0 > gui 1 > ros 2 > mcp 3 > motion_action 4，沿用既有 BASE_HOLD_S=0.5s 持有窗口更高优先级源持有底盘时，play 直接 busy；播放中被抢则整段抢断
base_host总电机开关、校准互锁、底盘速度/加速度、机械臂步长/校准范围最终裁决、0.5s watchdog条件不满足不写串口，并在阻塞请求的回复里返回真实原因
舵机串口唯一写入者仍是 base_hostMCP 崩溃不会留下第二个串口进程

开始、结束与抢断

  1. 开始：从 tracks 推导所需 lease。全身动作只有在 base 和 arm 同时可用时才启动，禁止先动一半再发现另一半 busy；机械臂先平滑靠近首帧，底盘首帧仍过加速度限制。
  2. 执行：两轨共享同一 monotonic start。机器变慢时各轨只取“此刻最新目标”（player.index_at() 一次二分跳到当前帧），绝不补播陈旧队列。机械臂靠既有 EE_STEP_MAX 每帧限幅自然平滑靠近首帧，不需要第二套 approach 逻辑。
  3. 正常结束：底盘强制补零速（needs_base_stop → 下一 tick stop(ser)），机械臂保持最后一帧并随后使用现有 idle auto-relax。动作最好主动回到安全姿态，但不是硬性依赖。
  4. 抢断（人工 或 ROS）：手柄、键盘、主臂跟随、GUI 或 motion_controller 的帧出现在被 lease 的域里，立即取消整个动作；底盘先停车，调用方收到 result: preempted + by: pad|gui|ros|mcp。不再叫 preempted_by_human（评审 P0，已采纳）——同一个 LLM 会先 turn_by（ros 级闭环）再 play，被 ros 抢断必须有名字，否则这条真实路径没有语义。
  5. 总安全门关闭：沿用现有九电机断输出；当前动作状态变为 safety_cut，重新开输出也不续播；同时正在进行的录制也中止并记进 last_result。
  6. 校准开始：校准帧同样算作人工 arm 输入，动作以 preempted by=calibrating 结束。

崩溃矩阵（评审 P0，已采纳）

发生什么行为可观测性
base_host 退出（串口掉线 → exit(1) → systemd 重启）退出路径先把阻塞中的 play 以 result: host_stopped, by: base_host 答复掉再关 socket；播放随进程消失，不续播；录制草稿丢失；control socket 由 RuntimeDirectory 重建客户端拿到的是结果而不是 EOF；status.host_started_at 变化，GUI 打印「草稿已丢失」
MCP server 进程被杀 / Hermes 重启socket 关闭 → Job.cancelled → 下一 tick result: aborted, by: client，底盘归零status.last_result 记录 aborted
SSH 在 save 中途断开旧动作文件完整（原子改名尚未发生），草稿留在板端内存GUI 报「保存失败（草稿保留）」，绝不谎报成功
GUI 切 Tab / 关窗切 Tab 主动发 stop + record-stop（含「已发出但板端尚未回报」的播放）；关窗则由 lease 超时和 watchdog 兜底日志一行；status 反映真实状态
主循环卡住超时阶梯只有一个真相源（control.py）：最长合法动作 15s < 服务端 JOB_MAX_WAIT_S=30s < 客户端 PLAY_TIMEOUT_S=40s。服务端先放弃，客户端拿到结构化的 control_timeout，动作按 aborted 处理不会有客户端永久挂死，也不会把「卡住」误报成 host_unreachable
禁止的 fallback 从臂未上线、校准进行中、动作文件损坏、control socket 连不上、lease 被抢、总输出关闭——任何一种都必须失败并说明原因。禁止偷偷换成绝对舵机值、旧缓存、近似动作或继续发完剩余帧。唯一的例外写在明处：control socket 建不起来时 base_host 照常提供遥控（并打 WARNING），因为让底盘为一个 runtime 目录陪葬是更坏的交易。

7 · 为什么不做“每个动作一个 MCP tool”

方案新动作发现问题判断
motion_action__yes()、motion_action__no() 动态增删 依赖 MCP client 重新拉工具表或支持 list_changed Hermes 是否刷新不应成为动作系统正确性的前提；动作名还可能撞保留名、非法字符或删除后残留缓存 不做
每次保存改 Hermes YAML 并 reload 能看到 把用户数据变化升级成配置变更；失败会污染大脑配置与现有 MCP 安全链 不做
固定 list/play/stop/status list 实时读目录 LLM 多一次 list 调用，但行为确定、无需重启、动作可增删改 采用

后续扩展边界
  • 可增加 aliases 或中文 label 帮助 LLM 选动作，但执行仍只认稳定 action_id。
  • 可增加“回到中位”自动尾段、动作组合和循环次数，但必须由服务端硬限制；MVP 不开放。
  • 若以后动作数量达到数百个，再考虑索引缓存和目录 watcher。现在扫描几十个小 JSON 比维护缓存一致性更可靠。
  • 若需要跨机器人共享动作，另做显式 export/import；不要让运行目录自动 Git 同步，因为不同机械校准仍需现场预览。

最终原则：GUI 负责管理，base_host 负责统一采集与最终裁决，文件负责描述，MCP 负责选择。LLM 永远拿不到串口，也永远绕不过人工抢断、底盘限速和机械臂校准范围。
