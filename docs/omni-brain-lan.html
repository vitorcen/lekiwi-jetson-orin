Omni 大脑:局域网端到端语音 + 工具调用

LeKiwi · Jetson Orin Nano 8GB + Mac(Apple Silicon) · 2026-07-25 · Qwen3-Omni-30B-A3B-Instruct-4bit / mlx-vlm 0.6.4 · Claude + codex gpt-5.6-sol 评审定稿 · 关键代码断言已逐条核实

TL;DR

  • 目标:Agent 页面新增一个「omni」大脑——用户语音直接喂给局域网上 Mac 的 Qwen3-Omni,模型自己听、自己想、自己调机器人工具、自己说话。不经 TTS,本地 ASR 只负责把用户说的话变成文字给 GUI 显示。
  • 核心洞察:把生成拆成「thinker 决策阶段」+「可选的 talker 语音阶段」。mlx-vlm 的 generate() 内部本来就是先跑完 thinker、再抽 hidden states、再跑 talker——工具调用与语音的冲突、性能浪费、文本漂移这三个问题,在拆开的那一刻同时消失。这不是调参,是数据流的正确切分。
  • hermes 走不通,别硬塞。它没有端到端的原生音频输出编排。板上 config 早就有 brain.kind 字段,但那只是死数据——switch_brain() 最后还硬编码写回 "kind":"hermes"。
  • Qwen3-Omni 原生支持 function calling(Hermes 风格 <tool_call>),官方 cookbook 证明了纯音频输入能吐 tool_call。但这只证明模型能力,不证明 mlx-vlm 这条路径已经能用——omnivla 现在手拼 ChatML,压根没调 apply_chat_template(..., tools=...),这部分必须新写并实测。
  • 工具执行不能 importlib 直接加载 MCP server。voice venv 没装 mcp/pyzmq,而且进程内的 _motion_lock 跨进程无效——两个进程各持一把锁等于没有锁。必须把业务逻辑抽成 import-clean 的共享模块。
  • 「GUI 零改动」「分流点只有一个」都是错的,已在正文更正。omni 需要原始音频,而现有链路在 ASR 之后就把音频丢了。
  • P0 已跑完:GO。实测(≥10 轮/场景,门在跑之前写死):工具调用成功率 100%、 tool dispatch P50 634 ms、聊天首音 P50 2561 ms(门 3500 ms)。 两阶段相对初稿方案在工具轮省掉中位 3.9 秒。
  • 流式是必需项,不是优化项。非流式首音 20.9 s;流式 chunk_size=50 配合回复长度约束(禁列表、两句内)后 2.6 s。 协议、服务端、板上播放从第一版就必须流式。

2 · 为什么不走 hermes

hermes(Nous Research Hermes Agent,本机 v0.19.0,装在 ~/.hermes/,板上以 systemd user 服务 hermes-gateway-robot 运行)的扩展性很好——几十个 model provider 插件、custom provider 支持任意 OpenAI 兼容 base_url,MCP function calling 接线完善。它的 gateway 甚至已经认识 input_audio 这种内容类型。

但它有一条结构性边界:没有端到端的原生音频输出编排。gateway 在部分会话/显示路径中会把音频内容降级成 [audio] 占位;更根本的是,它的 transport 抽象里没有「模型返回一段波形」这件事的位置。

强行走 hermes 意味着把 Qwen3-Omni 包成一个「既 OpenAI 兼容、又能收发音频」的端点,再让 hermes 装作看不见音频—— 为了复用一个不匹配的抽象而增加两层转译,同时把 hermes 的核心价值(MCP 编排)也丢了,因为 omni 的工具调度必须发生在音频轮内部。

更正:config「已预留」属实,「架构已预留」不属实 voice/voice_config.py:25 确有 "brain": {"kind": "hermes", "preset": "deepseek"} 和 omni:{url}, 但那只是死数据:voice_http.py 的 /brain 仍无条件按 hermes 校验 key_env/HTTPS/transport, daemon.py:2048 的 switch_brain() 最终硬编码写回 {"kind": "hermes", ...}。 这些都要改,不能声称「白捡」。

3 · Qwen3-Omni 的工具调用:能力、硬伤与正确解法

3.1 原生支持 Hermes 风格 <tool_call>

chat_template.json 里是完整的 Qwen/Hermes 工具协议:

{%- if tools %}
    {{- "# Tools\n\nYou may call one or more functions..." }}
    {%- for tool in tools %}{{- "\n" }}{{- tool | tojson }}{%- endfor %}
{%- endif %}
...
{%- if message.tool_calls %}
    {{- '<tool_call>\n{"name": "' }}{{- tool_call.name }}{{- '", "arguments": ' }}...{{- '}\n</tool_call>' }}
{%- elif message.role == "tool" %}
    {{- '\n<tool_response>\n' }}{{- content }}{{- '\n</tool_response>' }}

即 apply_chat_template(messages, tools=[...]) 直接生效,工具结果用 role:"tool" 回填。 mlx-vlm 的 apply_chat_template(..., **kwargs) 把 tools= 原样透传给 HF jinja 引擎。

3.2 音频输入 + 工具调用共存 —— 模型能力已证明,本项目路径未证明

官方 cookbooks/audio_function_call.ipynb 中,user turn 只有音频、没有文字,模型直接吐出 <tool_call>{"name": "car_ac_control", ...}</tool_call>。这确实是本方案需要的形态。

但不能把 cookbook 当作本项目的可行性证据 两条鸿沟:(1) cookbook 走的是 vLLM/transformers,不是 mlx-vlm;(2) omnivla 现有代码手拼 ChatML 字符串, 从未调用过带 tools= 的 chat template。「mlx-vlm 0.6.4 + 自定义 prompt 路径能稳定产出 tool_call」是一个待验证假设, 不是既成事实——它是 P0 的验收项之一,不是前提。 另注意 cookbook 自己的配置是 RETURN_AUDIO = False:官方演示 audio function call 时也关掉了 talker。

3.3 硬伤:talker 会念出工具 JSON

Qwen3-Omni 没有「只进思考不进语音」的机制 transformers 的 Qwen3OmniMoeForConditionalGeneration.generate() 中,talker 输入是 trailing_text_hidden = cat(assistant_hidden[:, 4:], tts_eos_embed)——把本轮 assistant 生成的 全部 token(除前 4 个模板 token)喂给 talker,无过滤、无截断、无标记位。 Qwen2.5-Omni 曾有可手工塞给 talker 的 thinker_reply_part 参数,在 Qwen3-Omni 的实现里已被删除(grep 零命中)。 官方唯一机制是全有/全无的 return_audio / disable_talker()。

3.4 正确解法:拆成 thinker 决策阶段 + 可选 talker 阶段

本文档初稿曾主张「永远 return_audio=True,发现 tool_calls 就丢弃音频」,论据是「talker 开销正比文本长度, 几十 token 的工具 JSON 很便宜」。这个论证是错的,评审时被推翻。

读 mlx-vlm 0.6.4 的实际代码(models/qwen3_omni_moe/qwen3_omni_moe.py:294-548), return_audio=True 的路径是四步,而不是「thinker 然后顺手 talker」:

generate(return_audio=True):
  ① generate_step(...)                        # thinker 自回归生成,直到 EOS   :394-410
  ② extract_thinker_hidden_states(...)        # 对 prompt+生成结果再做一次完整前向 :414-418
  ③ talker 生成 codec tokens                                                  :~420-517
  ④ code2wav 声码器                                                          :518-537
初稿错在哪 ② 是对整个 prompt + 生成结果的完整重新前向,音频编码路径也会再走一遍。它的开销由上下文总长度决定, 而不是由那几十个 token 的输出长度决定。④ 声码器还有固定开销。 所以工具轮浪费的绝不是「一行 JSON 的 talker」,而是整段 hidden-state 重算 + 固定声码器成本—— 初稿的成本模型整个搞反了。

而正确答案就摆在同一段代码里:① 和 ②③④ 之间有一条天然的缝。thinker 文本在任何 talker 计算开始之前 就已经完整可见。generate_stream()(:550-730)也是同样结构——它先把 thinker 跑到 EOS(:604-607), 才去抽 hidden states。

方案:两阶段适配层 
1. generate_thinker(prompt)          → thinker sequences + 文本
2. 解析工具标记
3. 有 tool_call  → 立即返回,根本不进入 ②③④,零浪费
4. 无 tool_call  → 用同一份 thinker sequences 继续 synthesize_audio()
纯聊天轮工具轮文本漂移talker 念 JSON
初稿:永远出音频1 次全流程1 次全流程(全浪费)无靠丢弃音频规避
先探测再出声2 次 thinker 生成1 次 thinker有无
两阶段(本方案)1 次全流程只跑 ①无结构上不可能

三个问题(工具 JSON 被朗读、性能浪费、文本漂移)在拆开的那一刻同时消失,而不是被逐个打补丁绕过。 这是数据流的正确切分,不是参数调优。

最小原型:把 generate_stream() 的 text yield 从 :699 提到 extract_thinker_hidden_states()(:610)之前,服务端看到工具标记就关闭生成器。 做成 omnivla 侧显式的适配层,不要 monkey-patch 业务判断——monkey-patch 已经用在修 mlx-vlm 的 bug 上了, 再拿它承载业务逻辑会让两种 patch 混在一起,升级时分不清哪个能删。

4 · 架构

板上麦克风 → VAD 切段
   ├→ 本地 ASR(并行)  → emit user_text → GUI 显示 + 进有界文本历史
   └→ 原始音频        → 局域网 → Mac omni server(常驻单进程,串行)
                                      ↓ ① thinker
                        ┌──── 解析工具标记 ────┐
                        │                      │
              有 tool_calls               无 tool_calls
                        │                      │
          返回 {turn_id, tool_calls}      ②③④ talker+code2wav
          板上执行 → POST tool-results     返回 24kHz 音频
          用 turn_id 续轮(不重传上下文)    板上原生播放

4.1 会话状态所有权:两个所有者,边界清晰

更正:初稿的「工具轮改发 ASR 文本」不是等价变换 它把模型实际听到的音频换成另一个 ASR 模型猜出来的文本。后果是模型可能否认自己刚才的意图、 误解工具结果、甚至改调别的工具——第一轮它是听着音频决定调工具的,第二轮却只看到一段可能识别错的文字。 这可以作为经 P0 对照测试验证过的优化,但不能当成架构公理写进设计。
所有者持有什么生命周期
Jetson跨用户轮的有界文本历史(按 token 预算裁剪)会话级
Mac当前工具链的临时 turn_id 状态:原始音频、预处理结果、thinker 文本、已发出的 tool_calls单轮;完成 / 取消 / TTL 到期即删

工具续轮只发 turn_id + tool_results,不让客户端重新拼一份语义不同的伪历史。 这样第二轮模型看到的仍是它自己听过的那段音频的上下文。

措辞更正 在 Mac 侧缓存 input_features 只能省掉网络传输和部分预处理; 当前 mlx-vlm 的 thinker 前向仍会走音频编码路径。可以说「避免重复传输与前处理」, 不能说「避免重新编码音频」。

4.2 板上执行面:必须抽共享模块,不能 importlib 加载 MCP server

初稿建议 importlib 直接加载 drive/mcp_server.py 调 call_tool(),理由是「三道安全门白送」。 事实核查后这条必须推翻:

初稿断言核实结果
call_tool()/list_tools() 是模块级函数、不依赖 MCP 会话✓ 成立(MCP 装饰器 return func)
drive 有钳位 + mutex + cooldown 三道门✓ 成立(drive/mcp_server.py)
「直接 import 即可,三道门白送」✗ 不成立,见下
「import 无副作用风险」✗ 不成立,顶层会建 ZMQ socket
  • voice/setup.sh 没装 mcp,也没装 pyzmq。在 voice venv 里 import 会直接在 from mcp... 炸掉,没有任何部署保证。
  • _motion_lock 和 cooldown 是进程内全局变量。hermes 拉起的 MCP 子进程和 voice-daemon 里的导入实例各持一份,互相看不见。两个进程各持一把锁 = 没有锁。「omni 模式下 hermes 不接管对话」并不能证明没有别的 hermes session 或入口会调它。
  • 直接调用装饰后的函数会绕过 MCP SDK 的 inputSchema 校验。
  • drive_move 跑在 asyncio.to_thread() 里,取消 coroutine 不会停止已在运行的线程——车会继续开到 duration 结束。
正确做法 把工具 schema 与业务逻辑抽到 import-clean 的共享模块(drive/tools.py、vlm/tools.py), MCP server 退化成薄适配层,omni executor 调同一批核心函数。 executor 层统一做 JSON Schema 校验、工具白名单、超时、结果大小上限。 运动互斥与 cooldown 必须下沉到单一拥有者(base_host 或独立 drive executor), 不能指望两个 Python 进程各自的模块锁。

这条没做完之前,P2 不允许用「前进一点」作正式验收——那等于在没有互斥的情况下让车动。

4.3 改动面:比初稿说的大得多

更正:「分流点只有一个」是严重低估 现有链路 _handle_chunk() → _asr_then_turn() → run_turn(gen, text) 中, run_turn 只收到文本,音频在 ASR 之后就被丢掉了。而 omni 需要原始音频。
本地 ASR 是一道闸,omni 模式下必须重新决策 _asr_then_turn() 现在用 classify_segment(text) 过滤:解码为空 / 语气词 / 过短的段 直接不起轮。在 hermes 模式下这是对的(大脑只吃文本,没文本就没得聊)。 但 omni 模式下,这等于让本地 ASR 替 omni 决定「这段话值不值得听」—— ASR 没听清的段,omni 未必听不清。
P2 必须明确二选一:(a) omni 模式跳过 classify_segment 闸,只靠 VAD 起轮(代价:噪声段也会打到 Mac); (b) 保留闸但放宽判据。不能默认继承。
组件改动
_asr_then_turn(gen, samples)保留 samples(现在手里有,只是没往下传);ASR 与网络请求并行;重新决策 classify_segment 闸
run_turn(gen, text, samples=None) 或独立 run_omni_turn()按 preset kind 分流
_barge_check() 起新轮同样要把 samples 传下去
新增原生音频播放函数见下,不能只是「直接 aplay」
TTS 队列 / _speak_worker不改,但 omni 是「绕过」而非「复用」——它根本不进那个队列
原生播放必须复刻完整播放语义 照 _local_play() 的结构写(它已经是 aplay 播 s16le,omni 的 24kHz 正好对得上 edge 那条路的采样率), 必须同时维护:set_state(SPEAKING)、_cur_aplay 句柄、generation 令牌比对、kill/reap、 _after_playback()、_playback_dead(rc) 设备失效重发现,以及 把 assistant 文本 append 进 _recent_tts——否则 barge-in 的回声检测失去参照,机器人会把自己的话当成用户插话。

4.4 GUI:不是零改动

更正:「GUI 零改动」是错的 下拉框选项确实数据驱动、Rust 白名单确实已放行 /brain 和 /config——所以「不改也能点」成立。 但「GUI 语义正确」不成立。

5 · 配置数据结构:消灭重复真相源

现状有四个真相源:brain.kind、brain.preset、顶层 omni.url、只描述 hermes provider 的 presets.*。 GUI 下拉框只提交 preset 名——后端凭什么推断出这个 preset 是什么种类? 没有定义。

改成 tagged union:kind 由 preset 自己携带,顶层 omni.url 删除。

{
  "brain": {"preset": "omni-mac"},
  "presets": {
    "deepseek": {"kind": "hermes", "api": "...", "model": "...", "key_env": "...", "pair": {...}},
    "omni-mac": {"kind": "omni",   "url": "http://<mac-lan-ip>:<port>",
                 "speaker": "ethan", "pair": {"asr": "sensevoice"}}
  }
}

向后兼容:老配置的 preset 没有 kind 字段时,默认解释成 "hermes"。 这样一个 preset 自己携带完整类型,「kind 与 preset 不一致」这个非法状态在数据结构层面不再存在。

6 · 协议

初稿的协议同时出现 session + 完整 messages + 独立 audio_b64 + 「messages 里 user 也可以带 audio」—— 三个真相源,典型的坏数据结构。重做如下。

不假装 OpenAI 兼容——它本来就不是(要流式回传音频、要按工具调用决定是否合成语音)。 假装兼容只会制造「看起来能用别的客户端打、实际不能」的误解。JSON + base64 对短语音够用,不必为「标准」引入 multipart。

响应用 SSE,因为板上已经有解析器 voice/daemon.py 的 _iter_sse() 现在用来读 hermes 的流,可直接复用——新链路零新增解析代码。 注意它那条注释里的实锅:不能用 aiohttp 的行迭代器(512KB read_bufsize 上限, 一行塞下整段 base64 音频会超限抛错、整轮中断),必须自行按 \n 切行。omni 的音频块比 hermes 的文本行大得多, 这个坑只会更容易踩到。

7 · 打断与取消:诚实地说,现有 barge-in 解决不了

更正:初稿说 barge-in「原样复用」,不成立 现有打断检测只在 SPEAKING 状态开麦(_handle_chunk() 的注释写得很清楚:「LISTENING 走正常截句; SPEAKING 开麦做打断检测;其余丢弃」)。于是:
  • Mac 推理期间 Jetson 处于 THINKING,用户语音被直接丢弃。
  • 非流式模式下,进入 SPEAKING 时 Mac 推理早已结束,已经没有东西可取消。
  • GUI 的 interrupt 能 cancel Jetson 的 aiohttp task,但同步的 MLX 推理不会因此停止,Mac 的 worker 还在跑。
  • 若此刻有 drive_move 在 asyncio.to_thread() 里,取消 coroutine 也不会停线程,车会继续开。

必须补齐:

  • Mac 侧请求级 cancel token,在 thinker / talker 的 token 循环里检查。
  • DELETE /v1/requests/{request_id} 取消端点。客户端断线不等于取消,必须走显式协议。
  • 取消当前工具链时,若有运动工具在途,显式调 drive_stop / motion controller stop——不能只 cancel 协程。
  • 定义「取消后 worker 多久必须重新可用」,并作为 P0 验收项。
  • 如果第一版做不到 THINKING 期打断,就诚实写「只支持播放期打断」,不要声称复用现有机制已经解决。

会话历史:采用有界文本历史,不做跨轮 KV cache

P2 初版没有任何跨轮记忆(每轮 system + 当前音频,说完就忘)。评估了「缓存语义空间」方案后, 选择有界文本历史,理由是实测数据而非偏好:

结论依据(codex 实测)
max_kv_size 是空操作 thinker 的 LanguageModel.make_cache() 强制返回普通 KVCache,而 make_prompt_cache() 一旦发现模型自带 make_cache() 就不看该参数。请求 512,返回的仍是 48 个普通 KVCache
RotatingKVCache 会算错位置 语言模型拿 cache._idx 当位置偏移,但它是环形写指针,写满跳回 keep,不是累计 token 位置。0.6.4 上禁用
mRoPE 不是障碍,但 RoPE offset 是 该版本 get_rope_index() 只给 image/video 建三维网格,音频走普通顺序位置。但 get_input_embeddings() 每次清空 _position_ids/_rope_deltas,只传 suffix 而不恢复 offset 会让 suffix 从位置 0 重来:logprob 平均偏差 0.22 → 1.31(最大 9.19)
KV cache 能省 280–300 ms/轮 2048 token 冷 prefill 339 ms,追加 128 token 仅 52 ms(6.5×)。20 轮约 2052 token
但冷 prefill 本来就只要 ~340 ms 在 2.5 s 首音预算里不显眼 → 有界文本历史够用
内存不是约束 96 KiB/token(48 层 × 4 KV head × 128 × 2B,GQA)。3 秒音频只有 40 token(13.3 token/s),20 轮 2052 token = 0.19 GiB。先撞上的是 65K 上下文上限,不是 128 GB
kv_bits 量化不值得 8-bit 让 suffix 从 105 ms 变慢到 289 ms,还引入漂移
静默损坏陷阱:历史音频不能只传当前那一段 历史里有多个音频段时,phase ② 必须重新提供所有历史音频 features。 只传当前音频,当前实现会把缺失的历史 audio embedding 补零——不报错,但语义是错的。 这正是本方案历史只存文本、不回放音频的直接原因。

若将来确实需要保留原始音频历史,再做跨轮 KV cache,但要手工管理三样东西:实际 token 序列(不是每轮重渲染模板)、 cache、RoPE offset。且优先级低于另一件事——把 ②③ 裁剪到最后一轮: _get_talker_assistant_parts() 完全不用 contextual hidden(只投影 assistant token embedding), _get_talker_user_parts() 也只在多模态位置用 hidden,所以裁剪是安全的,而 ② 的开销是线性的 (512→85 ms,2048→297 ms,4096→642 ms)。

  • 第一版不做网络流式 —— 此条作废。P0 实测:流式是必需项,不是优化项。 非流式首音 20.9 s,流式 chunk=50 + 回复长度约束后 2.6 s。协议、服务端、板上播放从第一版就必须是流式的, 详见第 6 节。

  • 不做 omni 的视觉输入。视觉仍走 vlm_look 返回文本 caption,与现有链路一致。
  • 不给 TTS 加 none 选项。omni 跳过 TTS 是 preset kind 分流的自然结果,不是 TTS 轴上的特殊值—— 往 TTS_ENGINES 塞哨兵值是把两个正交概念揉在一起。
  • 不补 required: []。JSON Schema 里缺 required 本就表示全部可选,补空数组没有语义价值 (初稿此处建议作废)。
